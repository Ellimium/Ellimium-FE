# 자산 폴더 연동 검증 (FE #2 · BE #2)

## 준비

- FE는 `feat/2-asset-folders`의 폴더 관리·자산 이동 구현을 사용한다.
- BE에 `20261006020520_add_asset_folders.sql`을 로컬 적용한다.
- FE `.env.local`은 `http://127.0.0.1:54321`과 로컬 anon key를 사용한다.
- 소유자 A와 다른 사용자 B를 **로컬 환경에만** 가입시킨다. 두 계정은 별도 브라우저 세션으로 연다.
- 작은 PNG 이미지 1개를 준비한다. 원격 프로젝트, 실제 사용자 데이터, secret/service role key를 사용하거나 기록하지 않는다.

BE에서 실행한다. `status` 출력의 키는 검증 기록에 복사하지 않는다.

```sh
npx supabase status
npx supabase migration up --local
npx supabase functions serve upload-asset
```

별도 터미널의 FE에서 실행한다.

```sh
npm run test:assets
npm run build
npm run dev -- --hostname 127.0.0.1
```

브라우저에서 `http://127.0.0.1:3000/assets`를 연다. Functions 실행과 업로드 성공까지 확인해야 신규 업로드 검증을 통과한 것으로 본다. 메타데이터 INSERT만으로 대체하지 않는다.

## 권한·실패 시나리오

- B로 접속하면 A의 폴더·개인 자산이 표시되지 않아야 한다. 룸에서 공유된 A의 이미지도 B의 개인 자산 관리 목록에 포함하지 않는다.
- 브라우저 Network에서 A의 폴더 이름 변경·삭제 또는 자산 이동 요청 형태를 확인한다. B 세션으로 같은 요청을 재현하되 A의 대상 ID를 사용한다. 인증 헤더·토큰·키를 문서나 로그에 남기지 않는다.
- 타인 행의 UPDATE/DELETE는 HTTP 오류가 아니라 영향받은 행 0개로 거부될 수도 있다. 단일 행 반환을 요구하면 `PGRST116`이 발생한다. 응답 성공 여부만 보지 말고 A의 원래 이름·폴더 연결이 유지되는지 재조회한다.
- A 자산을 B 폴더로 보내는 요청은 소유자 FK로 거부되어야 한다. 원래 폴더 연결을 보존한다.
- 로컬 검증 데이터에 한해, 화면에서 조회한 빈 폴더·미분류 자산의 소유권을 다른 테스트 사용자로 바꾼 뒤 새로고침 없이 변경을 시도하면 화면의 권한 거부 경로를 확인할 수 있다. 폴더 이름 변경·삭제와 자산 이동 모두 권한 또는 대상 소실 안내가 나타나야 하며, 변경 대상의 저장값은 그대로여야 한다. 자산 소유권 변경 시 경로의 소유자 제약도 맞춰야 하므로 실제 업로드 파일 대신 별도의 임시 메타데이터를 사용한다.
- 이동할 폴더를 선택한 다음 다른 세션에서 그 빈 폴더를 삭제하고 이동을 시도한다. 사용할 수 없는 폴더라는 안내가 나타나고 자산의 이전 위치가 유지되어야 한다.
- 로그아웃 상태에서 `/assets`를 열면 로그인 화면으로 이동해야 한다.

DB에서 실제 거부와 보존을 확인하는 자동 검증은 BE에서 실행한다.

```sh
npx supabase test db --local supabase/tests/asset_folders.sql
sh supabase/tests/asset_folders_upgrade.sh
```

첫 명령은 깊이·소유자·미인증 제한, 룸에서 조회 가능한 타인 자산 변경 거부, 삭제·이동 실패 후 데이터 보존을 확인한다. 두 번째 명령은 실제 마이그레이션 전후의 기존 자산 보존과 기존·새 자산의 미분류 기본값을 확인한다. 두 검증은 트랜잭션을 롤백한다.

## 합격과 정리

- 화면 시나리오와 권한·실패 시나리오가 기대 결과와 일치한다.
- FE 테스트·빌드와 BE 자동 검증이 모두 통과한다.
- 검증 후 만든 파일은 Storage API로 제거한다. 임시 자산 메타데이터와 빈 폴더·계정을 정리한다. 기존 개발 데이터는 삭제하지 않는다.
- 검증 전 실행 중이던 서비스는 유지하고, 이번 검증에서 시작한 브라우저·개발 서버·Functions 프로세스만 종료한다.
